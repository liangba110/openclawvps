## 2026-08-19 10:22 AI电商站云端任务静默停摆修复（老板先定位根因，我执行+验证）

**问题**：8/17 20:25 起云端任务全部静默停摆约 38h（schedule-runner/db-guard/watchdog/竞品情报等5个守护脚本），后台显示任务0执行、never_run、心跳未知；网站本身正常 200。

**根因（双重）**：
1. 调度脚本在 ubuntu crontab（*/5 * * * * schedule-runner-cloud.cjs >> /opt/ai-ecom-site/data/logs/schedule-runner-cloud-cron.log），但日志文件属主是旧用户 aiecom、权限 775 → ubuntu 写被拒 → 整条 cron 命令失败，脚本从未启动（syslog 确认 cron 有触发但失败）
2. 连锁失守：watchdog/db-guard/toc-guard/竞品情报等守护脚本同样写日志失败静默退出，且告警也写在失败日志里 → 无 QQ 告警

**修复（低风险，按老板方案）**：
1. `sudo chmod 666 /opt/ai-ecom-site/data/logs/*.log /opt/ai-ecom-site/data/logs/watchdog-state.json`（属主不变 aiecom，ubuntu 可写）
2. 手动跑 schedule-runner 验证心跳写入
3. 等 cron 周期确认自动恢复

**验证**：10:23/10:25 心跳OK自动恢复、watchdog-state lastCheck 更新、syslog 无 Permission denied、站点 200、pm2 ai-ecom-site online（aiecom 用户 20h 未受影响）

**遗留**：停摆期间错过的定时任务未补跑（老板未指示；可补 8/18 发布/情报任务）

**教训**：pm2 服务从 aiecom 迁到 ubuntu 时（8/15），crontab 也迁了但日志文件权限没跟 → 跨用户共享日志必须 666 或统一属主；守护脚本告警链路若依赖失败日志本身，会形成静默失守盲区 → 告警通道应与业务日志分离
