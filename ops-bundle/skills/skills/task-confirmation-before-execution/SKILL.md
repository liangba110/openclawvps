# 任务确认规则

## 核心原则

用户明确要求：**分配任务后，必须先理清意思并复述确认逻辑，等用户确认执行后，再修改网站程序代码和服务器数据。**

## 执行流程

1. **解读需求**：理解用户的任务描述
2. **复述确认**：用自己的话向用户复述你理解的意思和逻辑，**简洁明了，不要冗长**
3. **等待指令**：用户说"执行"或确认后，再动手
4. **修改代码/数据**：确认后才开始实际修改

## 信号识别

用户说以下话时，说明需要停下来重新确认：

| 用户的话 | 说明 | 行动 |
|---------|------|------|
| "不是" | 理解错了，重新梳理 | **立即停手**，问清楚再继续 |
| "先暂停" 或 "停" | 立即停手 | 停手，等新指示 |
| "不是去掉" / "不是xxx" | 方向不对 | 重新确认意图 |
| "不是" + 简短解释（如"不是去掉"） | 方向错，伴随纠正说明 | 根据纠正内容调整，**不要继续猜** |
| "全部优化一下" | 太模糊，无法执行 | 问"具体优化哪些方面？" |
| "还是不行" | 修改未生效 | **先排查**原因（缓存？逻辑？），**不要**直接继续改 |
| "还是不对" | 修改方向有误 | 停下来问哪里不对，不要自己猜 |

**关键**：用户说"不是"时，**不要继续猜测再改**——停下来重新问清楚。这是本会话最大的教训。

## 快捷命令 vs 纠正信号

用户说短句时，需要区分是"执行指令"还是"纠正信号"：

| 类型 | 例子 | 处理方式 |
|------|------|---------|
| **执行指令** | "执行", "改", "把XXX也显示出来", "颜色风格统一" | 确认后直接执行——这些是明确任务 |
| **纠正信号** | "不是", "不是去掉", "不对" | 停下来重新确认——这些是说你理解错了 |

区分方法：句末带"出来"、"一下"、"好"的是任务指令；"不是"、"不对"开头的是纠正信号。

## 排查优先于修改

用户说"还是不行/还是不对"时，正确流程是：

1. **先排查**：检查实际部署了什么、浏览器加载了什么、API返回了什么
2. **找到根因**：不要直接继续改代码
3. **确认再修**：告诉用户你发现了什么问题，确认后再改

**排查清单**（用户说"还是不行"时按顺序检查）：
1. 检查 Server 上实际部署的文件：`ssh ubuntu@host "grep 'title' index.html"`
2. 检查浏览器加载了什么 JS：`performance.getEntriesByType('resource').filter(r => r.name.includes('List-'))`
3. 检查 API 返回了什么数据：`curl API_URL`
4. 检查是否有 Service Worker 缓存（PWA）——这是最常见的"开发者看到新版本、用户看到旧版本"的原因
5. 检查 Server 上是否有旧 chunk 残留：`ls assets/List-*.js | wc -l`

**典型案例（来自本会话）**：

```
用户: 搭子页面的分类不显示
→ 我在浏览器测试发现分类其实是显示的。
→ 检查 Server 发现 4 代旧 chunk 残留，还有 Service Worker 缓存。
→ 根因：SW 缓存了旧版本，用户手机一直加载旧代码。
→ 修复：禁用 SW + 清理旧 chunk，而不是继续改代码逻辑。
```

## 错误示例（来自本会话——不要这么做）

```
用户: 首页游戏搭子的入口部分全部隐藏掉
我: (自行猜测是快捷入口) 删除快捷入口
用户: 不是
我: (又猜测是底部标签) 改底部标签
用户: 不是
...
→ 浪费大量时间，用户多次纠正
```

↑ 正确的做法应该是：**停下来问"你说的入口部分具体指哪些？快捷入口、底部导航、搜索栏？"**

## 正确示例（来自本会话）

```
用户: 搭子页面的分类不显示
我: 你的意思是分类筛选那一行现在没显示出来，需要它显示出来，对吗？
用户: 对的，执行吧
→ 确认后直接开工，一步到位
```

## 复述确认的格式

确认时格式应当：

1. **简洁**：1-2句话讲清你理解的内容
2. **留白**：最后加"是这样吗？确认了我再执行"或类似问句
3. **不猜**：不确定的部分明确提问，而不是自己假设

✅ 正确：`你的意思是把XXX隐藏掉，只保留YYY，是这样吗？`
❌ 错误：`我明白了，我来改XXX文件...`（直接动手）
❌ 错误：`我觉得应该是XXX...`（替用户做决定）

## 方案确认的格式（2026-08-28 工作协议升级）

用户工作协议（📖 `user-work-protocol` skill）把"先方案后执行"定为最高优先级，且方案必须结构化：

1. **目标**：一句话说清要达成什么
2. **步骤**：分步执行序列
3. **涉及的文件/工具**：要动哪些文件、用什么工具
4. **风险点**：会影响到什么（尤其现有系统/数据库/支付）
5. **预估产出**：完成后的可验证结果

新任务/新项目动手前先联网搜索 + GitHub 检索成熟方案，有则直接采用（注明来源），禁止重复造轮子。方案发出后等明确回复（"执行"）才动手；被否按意见修改重交。

## 禁止行为

- ❌ 不要跳步骤直接改代码
- ❌ 不要自行猜测用户意图后直接执行
- ❌ 不要在没有确认的情况下操作数据库或部署
- ❌ 用户说"不是"后不要继续猜测再改——停下来问
- ❌ 不要替用户做决定——不确定的部分直接提问

## 例外情况

- 紧急修复（网站挂了、数据丢失等）可以先修再补确认
- 用户明确说"直接做"或"执行"等明确指令
